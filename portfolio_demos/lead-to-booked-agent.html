Portfolio piece · Agent safety

An agent that takes real actions — and can explain every one of them

It receives an inbound lead from a webhook, holds an SMS conversation to qualify it, checks live calendar availability, books the appointment, writes the outcome back to a CRM, and notifies the business — with a human approval gate before anything irreversible.

The LLM handles conversation. Decisions and actions are governed by code, logged, and reversible — so the business can explain why any lead was tiered the way it was.

The problem

Demos show an agent talking. Clients need one that acts — safely.

The highest-ticket lead-response postings ask for an agent that books appointments, updates a CRM, and messages customers. Most demos stop at the conversation because the moment an agent writes to a real system, the questions get hard: what if the model misreads the address, double-books a slot, or texts someone who never consented?

This project puts every consequential decision in deterministic code the business can read, routes irreversible actions through an approval gate, and records every model call and tool call with its inputs, outputs, latency and cost. The conversation is the only part the LLM owns.

Architecture

A state machine with one gate that matters

Nodes are explicit and transitions are tested. Postgres checkpointing means a conversation can be interrupted and resumed mid-thread. The graph never imports a vendor SDK — SMS, calendar and CRM each sit behind a port with a mock and a real adapter.

The differentiator · deterministic qualification

The model never decides the tier

A rules engine reads config/qualification_rules.yaml and produces a tier, a numeric score, and a reasons[] list naming every rule that fired. Identical input always produces identical output. The rules are inspectable and changeable without touching code.

If the tier decision ever gets passed to the model, the build stops and flags it. The LLM extracts fields into a Pydantic model with per-field confidence — and never invents a value; missing stays missing.

The demo · approval gate

When confidence is low, it waits for a person

Below the confidence threshold, the graph checkpoints and queues the action. A reviewer approves, rejects, or edits-then-approves — each recorded with actor and timestamp. The default threshold is set so at least one scenario in the suite always lands here.

The eval story · scenario replay

Twenty scripted scenarios, identical every run

Each scenario is a YAML of inbound messages plus an expected outcome. With a stubbed LLM returning recorded responses, make scenarios produces identical results every time — and a failure prints which node diverged.

pass happy path → booked
pass out of service area → polite decline
pass ambiguous problem → asks clarifying Qs
pass lead goes silent → follow-up → close
pass no availability → offers alternatives
pass reschedule existing appointment
pass spam / abuse → disqualified, no contact
pass calendar API fails mid-book → handoff
pass duplicate submission of same lead
pass low-confidence extraction → approval gate

Run it

Clean clone to twenty passing scenarios, no credentials

Mock mode wires mock calendar, mock CRM and mock SMS behind the same interfaces the real adapters use. No test can send a real SMS or write to a real calendar — any that could is a bug.
